## О проекте

Этот репозиторий предназначен для хранения Jupyter Notebook и сопутствующих материалов, используемых при выполнении аналитических кейсов bootcamp 2026.

В рамках кейсов участники проходят полный путь от бизнес-вопроса и исходных данных до проверенной аналитической витрины и понятного результата для пользователя:

**бизнес-вопрос → гипотеза → данные → подготовка → расчёты → проверка качества → выводы → визуализация.**

Репозиторий следует рассматривать как рабочую базу знаний и практических решений. Ноутбуки должны не только содержать код, но и объяснять:
- какую задачу решает кейс;
- какие данные используются и как связаны;
- какие ограничения есть у выборки;
- как рассчитываются метрики;
- какие проверки подтверждают корректность результата;
- какие выводы можно сделать и чего данные утверждать не позволяют.

### Для кого этот репозиторий

- **Участникам bootcamp** — чтобы последовательно изучать материалы и выполнять практические задания.
- **Аналитикам** — чтобы понимать бизнес-смысл гипотез, метрик и результатов.
- **Data Engineers** — чтобы ориентироваться в источниках, преобразованиях, слоях данных и публикации витрин.
- **ML/LLM-специалистам** — чтобы понимать подготовку признаков, обучение/применение моделей и оценку качества.

## Что решает проект

Заказчик — игровая аналитика компании, анализирующая матчи Dota 2.

Общий бизнес-вопрос: **какие события матча, решения драфта и характеристики игрока связаны с вероятностью победы и насколько сильно?**

Результат аналитического кейса должен помогать отвечать на прикладные вопросы и представлять выводы в форме, понятной не только автору ноутбука.

Для каждой гипотезы желательно фиксировать один из статусов:

- **Подтверждена** — наблюдаемый эффект соответствует гипотезе и статистически обоснован.
- **Не подтверждена** — данные не поддерживают ожидаемый эффект.
- **Недостаточно данных** — объём или качество выборки не позволяют сделать надёжный вывод.

Статистическая значимость сама по себе не доказывает причинно-следственную связь. Если исследование наблюдательное, корректнее говорить о связи или ассоциации, а не о причинном влиянии.

## Архитектура и инструменты

По архитектурной схеме проекта поток данных организован следующим образом:

```text
Источники
  ├── PostgreSQL — справочники, матчи и игроки
  └── MongoDB    — события игрового процесса
          |
          v
      Загрузка / Airflow
          |
          v
      Lakehouse
      ├── RAW     — копия данных источников
      ├── STAGE   — очищенные и нормализованные данные
      └── MART    — бизнес-витрины для аналитики
          |
          v
      Trino — SQL-доступ к Iceberg-таблицам
          |
          v
      Superset — дашборды и визуальный анализ
```

Дополнительные компоненты платформы:

| Компонент | Назначение |
|---|---|
| **Portal** | Точка входа: описание платформы, метаданные и создание процессов |
| **JupyterHub** | Персональные notebooks, Spark-примеры и исследование данных |
| **Apache Airflow** | Оркестрация загрузок и преобразований, история DAG и логи задач |
| **PostgreSQL Metadata** | Метаданные схем, таблиц, watermark и запусков |
| **Apache Spark** | Чтение источников, очистка, приведение типов и преобразования |
| **Apache Iceberg** | Табличный формат Lakehouse, схемы, snapshots и транзакции |
| **MinIO** | Объектное хранение Parquet-файлов и метаданных |
| **Trino** | SQL-доступ к таблицам Lakehouse |
| **Apache Superset** | BI-дашборды и визуализация |
| **OpenLineage → Marquez** | Наблюдаемость и фиксация связей между DAG, источниками и таблицами |

### Слои данных

| Слой | Назначение | Ожидаемое содержимое |
|---|---|---|
| `RAW` | Сохранение исходных данных | Данные, максимально близкие к источникам |
| `STAGE` | Подготовка данных | Дедупликация, очистка, нормализация, типизация |
| `MART` | Аналитическое потребление | Бизнес-метрики, агрегаты и признаки для конкретных кейсов |

**Важно:** конкретные имена каталогов, схем и таблиц могут зависеть от конфигурации окружения. Перед запуском ноутбука сверяйтесь с фактическими именами в платформе и в самом ноутбуке.

### Кейс №3. Рошан и победа — SQL

**Вопрос:** насколько убийство Рошана связано с победой команды и зависит ли эффект от времени и числа убийств?

**Для кого:** игровые аналитики; результаты могут использоваться при подготовке рекомендаций командам.

**Основные гипотезы:**

- **H1. Первый Рошан:** если команда первой убивает Рошана, её win rate выше базового уровня.
- **H2. Время первого Рошана:** эффект может различаться в зависимости от временного интервала первого убийства Рошана.
- **H3. Повторные убийства:** если команда убивает Рошана чаще соперника, её win rate выше.

**Данные, указанные в постановке:**

| Источник / таблица | Используемые поля и назначение |
|---|---|
| `cs_events` | `match_id`, `steam_account_id`, `npcId`, `time`, `isFromIllusion` — события игрового процесса и убийства Рошана |
| `gold_events` | `match_id`, `steam_account_id`, `reason`, `amount`, `time` — события изменения золота; применимость зависит от реализации |
| `match_players` | `match_id`, `account_id`, `is_radiant` — привязка игрока к матчу и стороне |
| `matches` | `radiant_win`, `duration`, `lobby_type`, `game_mode` — исход и характеристики матча |

Для события Рошана в постановке указан `npcId = 133`; перед использованием необходимо сверить идентификатор с фактическими данными источника.

**Ключевая логика связей:**

```text
cs_events.match_id
    + cs_events.steam_account_id
          |
          v
match_players.match_id
    + match_players.account_id
          |
          v
match_players.is_radiant
          |
          v
matches.radiant_win
```

При подготовке данных важно:
- исключать события иллюзий, если они не должны учитываться;
- удалять дубли событий и записей игроков по согласованному правилу;
- проверять корректность времени события относительно длительности матча;
- учитывать матчи с неполными или некорректными данными;
- не приравнивать отсутствие найденного события к ошибке источника без дополнительной проверки.

**Ожидаемый результат:** аналитическая витрина с характеристиками убийств Рошана на уровне матча, результатами проверок качества и метриками для проверки гипотез.

### Кейс №22. Пики и контр-пики — ML

**Вопрос:** влияют ли сочетания героев (кто против кого) на исход матча сверх силы самих героев?

**Для кого:** аналитики и игроки, принимающие решения в драфте.

**Идея решения по постановке:**

1. Построить матрицу преимуществ «X против Y» на основе win rate.
2. Рассчитать ожидаемый win rate по общей статистике героев.
3. Выделить отклонения от ожидаемого преимущества.
4. Использовать SVD и эмбеддинги героев для поиска скрытых взаимодействий.
5. Применить модель для предсказания результата драфта.

**Гипотезы из постановки:**
- Для части пар героев win rate значимо отличается от ожидаемого.
- Добавление контр-пиков в модель драфта может улучшить качество предсказания.
- Найденные взаимодействия должны быть интерпретируемы через роли и характеристики героев.

**Данные из постановки:** `match_players`, `matches`, `heroes`. В частности, указаны идентификаторы матчей и героев, сторона игрока, победа, ранг, режим игры, роли и характеристики героев.

**Ожидаемый результат:** матрица контр-пиков, оценка качества модели и интерпретируемые взаимодействия героев.

### Кейс №23. Классификация ников — LLM

**Вопрос:** можно ли автоматически классифицировать ники игроков через LLM и отличаются ли полученные сегменты по игровым результатам?

**Для кого:** аналитики, работающие с профилями игроков: сегментация, фильтрация ботов и анализ токсичности.

**Идея решения по постановке:**

1. Получить уникальные ники из `players`.
2. Передать текст ника в LLM через доступный API.
3. Получить структурированную классификацию.
4. Сохранить результат в `stage.nick_classification` с инкрементом по `loaded_at`.
5. Присоединить классификацию к `match_players`.

**Гипотезы из постановки:**
- Точность классификации относительно ручной разметки достигает целевого уровня.
- Для ников с тегом команды или клана win rate может отличаться от среднего.

**Данные из постановки:** `players`, `match_players`, `matches`. Для LLM передаётся только текст ника — без `account_id`.

**Ожидаемый результат:** таблица классификации ников, оценка качества относительно ручной разметки и аналитика игровых показателей по сегментам.

## Типовой процесс выполнения кейса

Рекомендуемый общий процесс для всех кейсов:

```text
1. Постановка бизнес-вопроса
          |
          v
2. Формулировка гипотез и метрик
          |
          v
3. Изучение источников и схем данных
          |
          v
4. Подготовка RAW → STAGE
          |
          v
5. Построение MART
          |
          v
6. Data Quality checks
          |
          v
7. Расчёт метрик и проверка гипотез
          |
          v
8. Интерпретация и фиксация выводов
          |
          v
9. Superset / презентация результата
```

### 1. Постановка задачи

До написания SQL или Python-кода необходимо зафиксировать:
- заказчика и пользователя результата;
- бизнес-вопрос;
- гипотезы;
- метрики и способ их расчёта;
- критерии подтверждения или отклонения гипотез;
- ограничения исследования.

### 2. Работа с источниками

Для каждой таблицы нужно описать:
- систему-источник и слой данных;
- назначение таблицы;
- ключи и гранулярность;
- важные поля и их типы;
- связи с другими таблицами;
- возможные NULL, дубликаты и аномалии;
- требования к обновлению и полноте данных.

### 3. Преобразования

При построении STAGE и MART необходимо явно документировать:
- правила дедупликации;
- фильтрацию некорректных записей;
- преобразование типов;
- обработку пропусков;
- логику JOIN;
- уровень детализации результата;
- правила расчёта метрик.

### 4. Аналитика

Каждая гипотеза должна иметь:
- проверяемую формулировку;
- целевую и сравниваемую группы;
- метрику эффекта;
- размер выборки;
- метод статистической проверки;
- доверительный интервал;
- p-value или иной обоснованный критерий;
- интерпретацию и ограничения.

### 5. Публикация результата

Итоговая витрина должна иметь понятную схему, документированные поля и быть доступна аналитическим инструментам через Trino. В Superset следует строить графики, которые отвечают на бизнес-вопросы, а не просто отображают все доступные столбцы.

## Как начать работу

### Доступ к платформе

По инструкции платформы используются следующие сервисы:

| Сервис | Назначение | Как получить доступ |
|---|---|---|
| Portal | Главная точка входа | Выданные Portal username и password |
| JupyterHub | Работа с notebooks и Spark | Те же Portal credentials |
| Superset | BI и визуализация | Те же Portal credentials |
| Airflow | Мониторинг DAG и запусков | Те же Portal credentials |

Адреса сервисов и учётные данные следует брать из актуальной инструкции команды или Portal. Не храните пароли, токены и приватные адреса в Git.

### Общий порядок запуска

1. Получите доступ к платформе через Portal.
2. Откройте JupyterHub.
3. Перейдите к ноутбуку нужного кейса.
4. Проверьте, что доступны необходимые источники и Spark-сессия.
5. Выполняйте ячейки последовательно.
6. Убедитесь, что целевые таблицы появились в Lakehouse.
7. Проверьте результат SQL-запросом через Trino.
8. При необходимости откройте витрину в Superset.

### Требования к окружению

Точный набор версий библиотек и параметры Spark должны определяться конфигурацией платформы и конкретного ноутбука. Не следует устанавливать произвольные версии PySpark, Spark или Iceberg поверх управляемого окружения без согласования с командой.

Если ноутбук использует внешние библиотеки или API, необходимые зависимости, переменные окружения и способ безопасной передачи секретов должны быть описаны в самом ноутбуке или отдельной инструкции.

## Глоссарий

| Термин | Значение |
|---|---|
| **DAG** | Граф задач, описывающий последовательность выполнения процесса |
| **ETL** | Извлечение, преобразование и загрузка данных |
| **ELT** | Извлечение и загрузка данных с последующим преобразованием |
| **RAW** | Слой исходных данных |
| **STAGE** | Слой очищенных и подготовленных данных |
| **MART** | Аналитическая витрина для конкретной бизнес-задачи |
| **Lakehouse** | Архитектура хранения, объединяющая подходы Data Lake и Data Warehouse |
| **Iceberg** | Табличный формат для хранения и управления большими наборами данных |
| **Lineage** | Информация о происхождении данных и связях между объектами |
| **Data Quality (DQ)** | Проверки полноты, корректности, согласованности и уникальности данных |
| **Win rate** | Доля побед в рассматриваемой группе матчей |
| **SVD** | Метод матричного разложения, используемый в том числе для снижения размерности |
| **Embedding** | Векторное представление объекта, например героя |
| **LLM** | Большая языковая модель |
| **95% доверительный интервал** | Интервал оценки неопределённости статистического эффекта |
