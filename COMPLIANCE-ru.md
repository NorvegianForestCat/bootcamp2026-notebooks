# Комплаенс и управление качеством данных (Data Governance)

Данный документ описывает меры по обеспечению качества, безопасности, воспроизводимости и наблюдаемости данных в проекте **VERSION_2**. 

> **Важно:** Этот документ отражает **только реально реализованные** в проекте механизмы. Любые функции, не внедрённые в код (например, криптографическое шифрование данных в покое или автоматический retention), здесь не упоминаются, чтобы не вводить в заблуждение.

---

## 1. Качество данных (Data Quality)

Пайплайн реализует строгие проверки качества на каждом слое архитектуры Medallion (RAW → STAGE → MART) с использованием движка `lakehouse_dq.py`.

### Уровни строгости проверок:
- **HARD:** При нарушении пайплайн немедленно останавливается, данные не публикуются в витрину. Примеры:
  - Отсутствие обязательных полей (`match_id`, `radiant_win`).
  - Нарушение уникальности первичных ключей после дедупликации.
  - Некорректные типы данных или значения вне допустимых диапазонов (например, `duration < 600` секунд).
- **QUARANTINE:** Бракованные записи изолируются в специальные таблицы (`lakehouse.quarantine.*`), а чистые данные продолжают обработку. Примеры:
  - Матчи с неполным составом (`human_players != 10`).
  - События с некорректным временем (`time < 0` или `time > duration`).

### Ключевые проверки для Кейса №3 (Рошан):
1. **Целостность сумм:** `roshan_killed_by_radiant + roshan_killed_by_dire + roshan_killer_side_unknown == total_roshan_kills`.
2. **Валидность таймингов:** Интервал между убийствами Рошана в одном матче ≥ 480 секунд.
3. **Ссылочная целостность:** 100% записей в STAGE имеют валидные `match_id` и `hero_id`, существующие в справочниках.

## 2. Защита персональных данных (PII и 152-ФЗ)

Проект обрабатывает данные, которые могут быть отнесены к псевдонимизированным персональным данным (Steam `account_id`, `personaname`).

### Реализованные меры:
- **Минимизация:** В аналитические витрины (MART) не передаются прямые идентификаторы (`personaname`). Используется только `account_id` как суррогатный ключ для агрегации.
- **Фильтрация анонимов:** Записи с `account_id = 4294967295` (анонимный профиль Steam) исключаются из обработки на этапе STAGE.
- **Отсутствие шифрования:** В рамках данного учебного проекта данные в PostgreSQL, MongoDB и MinIO хранятся в открытом виде. Криптографическое шифрование на уровне приложения или хранилища **не реализовано**.

---

## 3. Наблюдаемость и линейность данных (Data Lineage)

Для обеспечения прослеживаемости преобразований используется стандарт **OpenLineage** с визуализацией в **Marquez**.

### Реализованные механизмы:
- Каждый шаг PySpark-джобы (чтение из RAW, запись в STAGE/MART) обёрнут в контекстный менеджер `ctx.lineage()`.
- В события линейности передаются:
  - Имя задачи (Job Name).
  - Входные наборы данных (Inputs).
  - Выходные наборы данных (Outputs).
  - Описание выполненного преобразования.
- Это позволяет при возникновении инцидента быстро определить, какой источник или этап преобразования стал причиной некорректных данных в витрине.

---

## 4. Управление рисками моделей (Model Risk Management, MRM)

На текущий момент в `VERSION_2` реализован только аналитический кейс на базе SQL/PySpark (Кейс №3). Машинное обучение (ALS, LLM) не развёрнуто.

### Применимые к текущему кейсу меры:
- **Статистическая валидация:** Все гипотезы проверяются с расчётом p-value и 95% доверительных интервалов (метод Уилсона).
- **Контроль утечки данных (Leakage):** Признаки для агрегации рассчитываются строго на основе исторических данных слоя STAGE, без использования пост-фактум метрик, недоступных на момент события.
- **Воспроизводимость:** Все преобразования детерминированы. Генератор данных использует фиксированный seed (`--seed`), что гарантирует идентичность наборов данных при повторных запусках.

---

## 5. Контроль доступа (Access Control)

Управление доступом реализовано на базовом уровне, соответствующем учебному окружению.

### Реализованные механизмы:
- **Сетевая изоляция:** Сервисы (PostgreSQL, Mongo, MinIO, Airflow) проброшены только на `127.0.0.1` (localhost), что предотвращает несанкционированный доступ из внешней сети.
- **Аутентификация:** Доступ к Airflow и Superset защищён базовой аутентификацией (логин/пароль), заданными через переменные окружения `.env`.
- **Отсутствие RBAC:** Детализированное управление ролями (Row-Level Security или Fine-Grained Access Control) в Trino/Superset **не настроено**. Все авторизованные пользователи имеют равный доступ к витринам.

---

## 6. Реагирование на инциденты (Incident Response)

В случае сбоя пайплайна (например, падение задачи Airflow из-за нарушения HARD DQ-правила):

1. **Автоматическая остановка:** Пайплайн прерывается, некорректные данные не записываются в целевые таблицы Iceberg.
2. **Логирование:** Причина сбоя (например, `[DQ HARD FAIL] ... нарушено в 15/10000 строк`) фиксируется в логах задачи Airflow.
3. **Изоляция:** Если сбой вызван правилом QUARANTINE, бракованные записи сохраняются в `lakehouse.quarantine.*` для последующего ручного анализа.
4. **Восстановление:** После исправления источника данных или кода преобразования DAG можно перезапустить с упавшей задачи. Благодаря идемпотентности операций (`MERGE INTO` в RAW и `createOrReplace` в STAGE/MART), повторный запуск не создаст дубликатов.

---

## 7. Ограничения архитектуры (Честное декларирование)

Для полной прозрачности ниже перечислены механизмы, которые **отсутствуют** в текущей реализации:

| Механизм | Статус | Обоснование / Компенсирующая мера |
|---|---|---|
| **Инкрементальная загрузка в STAGE/MART** | ❌ Не реализовано | Используется полный пересчёт (`createOrReplace`). Это гарантирует корректность неаддитивных агрегатов (винрейт, квантили) при минимальных усилиях по поддержке. Инкремент реализован только в RAW. |
| **Автоматический Retention (очистка)** | ❌ Не реализовано | Таблицы журналов (`cleanup_runs`) созданы в схеме БД, но джобы автоматической очистки не настроены. Данные накапливаются. |
| **Шифрование данных (At Rest / In Transit)** | ❌ Не реализовано | Учебный проект, развёртываемый локально через Docker. |
| **Машинное обучение (ML/LLM)** | ❌ Не реализовано | В `VERSION_2` реализован только Кейс №3 (SQL-аналитика). Кейсы №20-23 остаются в стадии исследовательских ноутбуков в `VERSION_1`. |
