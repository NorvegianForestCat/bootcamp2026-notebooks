## 1. День 1 — Бизнес-аналитика и исследование данных

**Главный вопрос:** что хотим узнать и какие данные для этого нужны?

**Роли:** бизнес-аналитик, Data Analyst, Product Analyst.

| № | Артефакт | Содержание / критерий готовности | Где должен находиться |
|---|---|---|---|
| 1 | Постановка бизнес-задачи | Заказчик, проблема, бизнес-вопрос, ожидаемое решение и полезный результат | **Figma:** блок «Постановка задачи»; **GitHub:** описание кейса в README или вводной ячейке ноутбука |
| 2 | Распределение ролей | Участники, зоны ответственности, передача результатов между ролями | **Figma:** блок команды / постановки задачи; **GitHub:** при необходимости — README кейса |
| 3 | Реестр гипотез | Для каждой гипотезы: формулировка, необходимые данные, метрика и метод проверки | **Figma:** карточки кейсов; **GitHub:** Markdown-раздел ноутбука «Гипотезы» |
| 4 | Каталог источников | Источник → таблица/коллекция → назначение → необходимые поля | **GitHub:** `learn/` — точный файл требуется сверить; **Notebook:** раздел «Источники данных» |
| 5 | Отчёт первичного Data Quality | NULL, дубликаты, аномалии, типы, форматы и проблемы ключей; для каждой проблемы — причина, влияние и решение | **GitHub:** исследовательский ноутбук кейса; **Figma:** заметки / схема данных, если вынесены на доску |
| 6 | ER-диаграмма | Сущности, ключи, связи и направление зависимости | **Figma:** схема связей данных; **GitHub:** экспорт диаграммы или ссылка из документации — проверить наличие |
| 7 | Спецификация преобразований | Источник → очистка → объединение → преобразование → агрегация → витрина | **Figma:** схема данных / ETL; **GitHub:** описание преобразований в ноутбуке |

**Итог дня:** бизнес-задача, роли, проверяемые гипотезы, исследованные источники, проблемы качества, ER-диаграмма, список преобразований и требования к данным.

## 2. День 2 — Системная аналитика и Data Engineering

**Главный вопрос:** как технически получить, подготовить, хранить и обновлять данные?

**Роли:** Data Engineer, системный аналитик, архитектор.

| № | Артефакт | Содержание / критерий готовности | Где должен находиться |
|---|---|---|---|
| 1 | Архитектурная схема | Источники, оркестрация, обработка, хранение и потребители | **Figma:** архитектурная схема платформы |
| 2 | Модель DWH / Lakehouse | Слои RAW, STAGE, MART, назначение и гранулярность таблиц | **Figma:** схема Lakehouse; **GitHub:** SQL/PySpark-ячейки и описание таблиц |
| 3 | Спецификация ETL | Извлечение, очистка, преобразования, загрузка, правила обработки ошибок | **GitHub:** `learn/` и ноутбук кейса; точные имена файлов требуют сверки |
| 4 | Спецификация потоков | Источники и целевые объекты, зависимости, расписание и триггеры | **Figma:** блок Airflow / схема потоков; **Airflow:** DAG и история запусков |
| 5 | Data Lineage | Происхождение данных: источник → процесс → таблица → витрина | **Figma:** блок OpenLineage → Marquez; **Marquez:** фактический lineage |
| 6 | Регламент обновления | Частота, watermark, инкрементальная загрузка, повторный запуск | **GitHub:** ETL-код и описание логики; **Airflow:** расписание DAG |
| 7 | SLA витрин | Источник, частота обновления, глубина хранения, актуальность, время доступности, реакция и восстановление | **GitHub:** документ/Markdown SLA; **Figma:** архитектура и потребители; значения должны быть согласованы с командой |
| 8 | Техническая документация | Таблицы, поля, ключи, типы, ограничения и зависимости | **GitHub:** README/документация кейса; **Portal:** метаданные |

**Итог дня:** архитектура, модель DWH/MART, ETL-процессы, описание потоков, lineage, логика обновления, SLA и согласованное техническое решение.

### Перечень файлов `learn`

| Файл / папка | Назначение | День |

| Поле | Что указать |
|---|---|
| Название файла | Точное имя с расширением |
| Тип | Notebook, SQL, Markdown, CSV, PDF и т. д. |
| Описание | Какую тему или практическую задачу покрывает файл |
| Входные данные | Какие файлы/таблицы/источники нужны |
| Результат | Что участник должен понять или получить после выполнения |

| Ссылка | Прямая GitHub-ссылка на файл |

### Перечень `learn/`: почему он пока не заполнен именами файлов

Пользователь отдельно запросил полный перечень файлов в разделе `learn`. Для точного перечня необходим фактический вывод GitHub API или архив репозитория. Веб-открытие корня репозитория и каталога не вернуло содержимое, поэтому нельзя достоверно указать:
- существующие подпапки;
- точные имена файлов и расширения;
- назначение каждого файла;
- зависимости и порядок изучения.

Не заменяйте этот перечень догадками. После получения ZIP репозитория или вывода `tree learn` таблицу следует заполнить по фактическим файлам.

Команда для получения дерева каталога локально:

```bash
git clone https://github.com/NorvegianForestCat/bootcamp2026-notebooks.git
cd bootcamp2026-notebooks
find learn -type f | sort
```

Для Windows PowerShell:

```powershell
git clone https://github.com/NorvegianForestCat/bootcamp2026-notebooks.git
Set-Location bootcamp2026-notebooks
Get-ChildItem .\learn -Recurse -File | Select-Object -ExpandProperty FullName
```

## 11. Финальный чек-лист закрытия реестра

- [ ] Сверить фактическое содержимое Yandex Whiteboard по экспорту PDF или скриншотам.
- [ ] Зафиксировать точные названия фреймов и ссылки на объекты Figma.
- [ ] Получить фактический список файлов и подпапок `learn/`.
- [ ] Описать каждый файл `learn/`: назначение, входы, результат и день.
- [ ] Привязать ноутбуки кейсов к артефактам соответствующих дней.
- [ ] Проверить, что у каждого артефакта есть владелец, статус и место хранения.
- [ ] Добавить прямые ссылки на GitHub-файлы, Figma-фреймы и доску Yandex.
- [ ] Отметить артефакты, которые должны быть созданы командой, но пока отсутствуют.

**Критерий готовности реестра:** новый участник может по каждому дню увидеть ожидаемый результат, понять, где он хранится, открыть исходный материал и проверить его статус.
