# Incident Response Runbook — Аналитические кейсы Dota 2 (VERSION_2)

**Версия:** 2.0 (Production)  
**Область:** Lakehouse, Airflow, Spark, Trino, Superset  
**База:** SLA (классификация инцидентов P1–P4)  
**Актуальность:** Документ адаптирован под реализованный ETL-пайплайн (Кейс №3). Сценарии ML/LLM исключены как нереализованные.

---

## 1. Цель

Единая процедура реагирования на инциденты: фиксация, классификация, эскалация, устранение, восстановление, документирование.

---

## 2. Классификация инцидентов

| Приоритет | Уровень | Описание | Пример | Время реакции | Время восстановления |
|-----------|---------|----------|--------|---------------|----------------------|
| **P1** | Критический | Полная недоступность или существенная недостоверность результата | Повреждение витрины, массовая ошибка расчётов | ≤ 30 мин | ≤ 4 ч |
| **P2** | Высокий | Нарушена основная функциональность пайплайна | ETL завершился ошибкой, DQ HARD FAIL | ≤ 2 ч | ≤ 8 ч |
| **P3** | Средний | Частичная ошибка, не препятствующая использованию результата | Некорректно рассчитана отдельная метрика | ≤ 8 раб. ч | ≤ 2 раб. дня |
| **P4** | Низкий | Незначительная проблема документации или представления | Ошибка описания поля в Data Dictionary | ≤ 2 раб. дня | ≤ 5 раб. дней |

## 3. Процедура реагирования

### Шаг 1 — Фиксация проблемы
Создать запись в инцидентном журнале (Jira/GitHub Issues):
- `incident_id`: Уникальный ID
- `title`: Краткое название
- `priority`: P1–P4
- `detected_at`: Время обнаружения
- `affected_datasets`: Затронутые таблицы/витрины
- `description`: Описание проблемы

### Шаг 2 — Классификация приоритета
Использовать таблицу из раздела 2. Если неясно — присвоить более высокий приоритет.

### Шаг 3 — Эскалация
- **P1:** Team Lead + Data Engineering Lead (Телефон/мессенджер срочно)
- **P2:** Team Lead + Data Engineering Lead (Мессенджер + email)
- **P3:** Team Lead (Мессенджер)
- **P4:** Ответственный разработчик (Email / задача в трекере)

### Шаг 4 — Диагностика
1. Проверить логи Airflow (DAG runs, task logs).
2. Проверить логи Spark (executor, driver).
3. Проверить DQ-проверки (какие правила упали: HARD или QUARANTINE).
4. Проверить lineage в Marquez (откуда пришли «плохие» данные).
5. Проверить Iceberg snapshots (какая версия витрины повреждена).

### Шаг 5 — Локализация (containment)
- Приостановить зависимые пайплайны.
- Не удалять повреждённую витрину — оставить для форензики.
- При необходимости откатить на предыдущий Iceberg snapshot.

### Шаг 6 — Устранение
- Исправить код/данные/конфигурацию.
- Получить одобрение Data Engineering Lead.

### Шаг 7 — Проверка качества
После устранения:
1. Запустить все обязательные DQ-проверки для затронутых витрин.
2. Убедиться, что `is_sum_valid = true` (для кейса №3).

### Шаг 8 — Восстановление
- Повторно запустить пайплайн.
- Убедиться, что витрина доступна через Trino.
- Зафиксировать время восстановления.

### Шаг 9 — Документирование
Заполнить инцидентный отчёт (root_cause, fix_description, lessons_learned).

## 4. Специфичные сценарии

### Сценарий A: DQ HARD FAIL в ETL
**Признаки:** Airflow задача упала с `[DQ HARD FAIL]`.  
**Действия:**
1. Определить упавшее правило (rule_id, description).
2. Оценить количество нарушённых строк.
3. Исправить источник или правило очистки.
4. Повторно запустить с того же этапа (идемпотентно через MERGE INTO или createOrReplace).

### Сценарий B: DQ QUARANTINE
**Признаки:** Строки изолированы в `lakehouse.quarantine.*`.  
**Действия:**
1. Проанализировать причину попадания в карантин.
2. Если данные можно восстановить — исправить и перезагрузить.
3. Если данные потеряны — задокументировать как потерю.

### Сценарий C: Повреждение Iceberg таблицы
**Признаки:** Ошибка чтения, некорректные данные в витрине.  
**Действия:**
1. Проверить Iceberg snapshots.
2. Откатить на предыдущий корректный snapshot.
3. Проверить lineage (какое преобразование вызвало повреждение).
4. Повторно запустить преобразование.

## 5. Связь со SLA

- Время реакции и восстановления соответствуют SLA.
- Количество автоматических повторных попыток: до 3.
- Интервал между попытками: 5–15 мин.
- Публикация некорректной витрины запрещена.
- Контрольная проверка после запуска обязательна.

## 8. Мониторинг доступности сервисов (Healthchecks)

Инфраструктура `VERSION_2` использует встроенные механизмы самодиагностики (healthchecks) для критически важных сервисов. Оркестратор Docker использует эти проверки для управления зависимостями запуска (например, Airflow и Marquez ждут статуса `service_healthy` от PostgreSQL перед стартом).

**Реализованные проверки:**
- **PostgreSQL**: `pg_isready -U ${PG_USER}` (проверка готовности СУБД принимать подключения).
- **MongoDB**: `mongosh --quiet --eval 'db.runCommand({ping:1})'` (проверка отклика базы данных).
- **RustFS (S3-совместимое хранилище)**: `wget -qO- http://127.0.0.1:9001/health` (проверка доступности API хранилища).
- **Airflow Webserver**: `curl -f http://127.0.0.1:8080/health` (проверка доступности UI и API оркестратора).

*Примечание:* Сервисы `Spark`, `Trino`, `Superset` и `Marquez` не имеют явных HTTP-проверок в данной конфигурации, но их запуск строго привязан к успешному прохождению healthcheck зависимых сервисов (в первую очередь PostgreSQL) через механизм `depends_on: condition: service_healthy`.

## 9. Профилактика

- Ежедневный мониторинг DQ-проверок.
- Еженедельный обзор проваленных джоб Airflow.
- Ежемесячный обзор инцидентов и извлечение уроков.
- Регулярное тестирование отката (rollback) на staging.
