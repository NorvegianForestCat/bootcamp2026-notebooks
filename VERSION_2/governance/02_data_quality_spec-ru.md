# Спецификация Data Quality (DQ) для Lakehouse Dota 2 (VERSION_2)

Данный документ описывает правила контроля качества данных для архитектуры Medallion (`RAW` → `STAGE` → `MART`) в рамках реализованного пайплайна **Кейса №3: Влияние убийства Рошана на исход матча**.

---

## 1. Базовые требования по слоям Lakehouse

### Слой 1: Источники → `RAW` (Контроль доставки)
Поскольку источники PostgreSQL и MongoDB хранят данные ограниченное время, критически важно проверять полноту и своевременность перелива.

#### Актуальность / Timeliness (`DQ-RAW-01`)
* **Правило:** Максимальное значение `loaded_at` в `raw.pg__matches` должно отставать от времени запуска DAG не более чем на заданный порог (буфер безопасности).
* **Реакция:** *Hard Fail* (остановка пайплайна и алерт).

#### Уникальность событий MongoDB (`DQ-RAW-02`)
* **Правило:** Строковое представление `_id` (ObjectId) уникально во всех коллекциях событий (`cs_events`, `gold_events`, `tower_death_events`).
* **Реакция:** *Hard Fail*.

---

### Слой 2: `RAW` → `STAGE` (Очистка, фильтрация и валидация сущностей)

#### Уникальность матчей и слотов игроков (`DQ-STG-01`)
* **Правило:** `match_id` уникален в `stage.case03_pg__matches`; составной ключ `(match_id, player_slot)` уникален в `stage.case03_pg__match_players`.
* **Реакция:** *Hard Fail* (после дедупликации по `loaded_at DESC`).

#### Обязательные поля матча (`DQ-STG-02`)
* **Правило:** Поля `match_id`, `start_time`, `duration`, `radiant_win` строго `NOT NULL`.
* **Реакция:** *Hard Fail*.

#### Фильтрация длительности матчей и валидность состава (`DQ-STG-03`)
* **Правило:** Отсекаются несостоявшиеся/быстрые матчи: `duration >= 600 AND duration <= 18000` (от 10 минут до 5 часов). Количество игроков: `human_players = 10`.
* **Реакция:** *Quarantine* (отсев из витрин, логирование в Data Funnel).

#### Валидность слотов и героев (`DQ-STG-04`)
* **Правило:** `player_slot IN (0, 1, 2, 3, 4, 128, 129, 130, 131, 132)`; `hero_id > 0`.
* **Реакция:** *Quarantine*.

#### Комплектность составов 5v5 (`DQ-STG-05`)
* **Правило:** Для каждого валидного `match_id` в `stage.case03_pg__match_players` присутствует ровно 10 записей (5 игроков за Radiant и 5 за Dire).
* **Реакция:** *Quarantine*.

#### Валидность игрового времени событий (`DQ-STG-06`)
* **Правило:** Поле `time >= 0` и `time <= duration` матча.
* **Реакция:** *Quarantine*.

---

### Слой 3: `STAGE` → `MART` (Ссылочная целостность и бизнес-логика)

#### Целостность внешних ключей (`DQ-MRT-01`)
* **Правило:** 100% `hero_id` из `stage.case03_pg__match_players` присутствуют в `stage.case03_pg__heroes`; 100% `match_id` из событийных таблиц существуют в `stage.case03_pg__matches`.
* **Реакция:** *Hard Fail* перед сборкой витрин.

#### Специфические проверки для Кейса №3 (Рошан)

##### Согласованность событий убийства Рошана (`DQ-CASE3-01`)
* **Правило:** На каждое событие добивания Рошана в `cs_events` (`npcId = 133`, `time > 0`) в том же матче и в окне `±5 секунд` должно приходиться ровно 5 записей начисления командного золота в `gold_events` (`reason = 'ROSHAN'`) для игроков победившей Рошана стороны.
* **Реакция:** *Quarantine* (исключение матча с рассинхронизированными логами из расчёта).

##### Адекватность таймингов возрождения Рошана (`DQ-CASE3-02`)
* **Правило:** Первый Рошан не может быть убит до выхода крипов (`time >= 0`). Интервал между последовательными убийствами Рошана внутри одного `match_id` должен составлять не менее 480 секунд (минимальный таймер респавна Рошана — 8 минут).
* **Реакция:** *Quarantine*.

##### Целостность сумм убийств Рошана в MART (`DQ-MRT-02`)
* **Правило:** Для каждой записи в `mart.case03_pg__match_roshan_mart` должно выполняться условие:  
  `roshan_killed_by_radiant + roshan_killed_by_dire + roshan_killer_side_unknown = total_roshan_kills`
* **Реакция:** *Hard Fail*.

##### Диапазон вероятностей в MART (`DQ-MRT-03`)
* **Правило:** В витрине `mart.case03_pg__roshan_time_effect` поле `first_roshan_win_rate` должно находиться строго в диапазоне `[0, 1]`.
* **Реакция:** *Hard Fail*.

## 2. Реализация проверок на PySpark

Проверки реализованы в модуле `src/jobs/case_3/dq_checks.py` и интегрированы в Airflow DAG как отдельный `quality_layer`.

### Архитектура DQ-движка
1. **HARD правила:** Если количество нарушений > 0, пайплайн останавливается с ошибкой `RuntimeError`, предотвращая публикацию некорректных данных.
2. **QUARANTINE правила:** Нарушающие строки изолируются в таблицы `lakehouse.quarantine.*` с указанием причин (`dq_failed_rules`), а чистые данные продолжают движение по пайплайну.
3. **Data Funnel:** На этапе STAGE фиксируется и логируется точное количество и процент строк, удаленных на каждом шаге фильтрации.

### Пример кода проверки (DQ-MRT-02)
```python
def validate_mart_roshan_sum(spark: SparkSession) -> int:
    query = """
        SELECT count_if(
            (roshan_killed_by_radiant + roshan_killed_by_dire + roshan_killer_side_unknown) != total_roshan_kills
        ) as violations 
        FROM lakehouse.mart.case03_pg__match_roshan_mart
    """
    return spark.sql(query).first()["violations"]
```
