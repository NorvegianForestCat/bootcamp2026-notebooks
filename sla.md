# SLA — Service Level Agreement
## Регламент качества и надёжности аналитических кейсов

**Версия:** 1.1  
**Статус:** Проект документа (Draft)  
**Технологический стек:** Apache Spark (PySpark), Apache Airflow, Iceberg, MinIO, Trino, Apache Superset, Python, ML-модели и внешние API.

> Все числовые нормативы в документе являются предварительными целевыми значениями. Они подлежат согласованию с командой и уточнению после оценки фактических возможностей инфраструктуры.

---

# 1. Общие положения

## 1.1. Назначение документа

Настоящий документ определяет требования к качеству, надёжности, воспроизводимости и корректности аналитических решений, реализуемых в рамках проекта.

SLA устанавливает:
- требования к входным данным;
- требования к обработке и преобразованию данных;
- требования к корректности аналитических результатов;
- правила проверки качества данных (Data Quality);
- требования к воспроизводимости вычислений;
- требования к сохранению результатов в Lakehouse;
- требования к использованию ML-моделей и внешних API;
- критерии приёмки аналитических кейсов.

## 1.2. Область действия

Документ распространяется на следующие аналитические кейсы:

| № | Название кейса | Основная технология |
|---|---|---|
| 3 | Корреляция между временем убийства Рошана и победой | PySpark / SQL |
| 20 | Сегментация героев по пику и контр-пику | PySpark / ALS |
| 21 | Классификация ников игроков | Python / LLM API / Spark |

Основным объектом SLA являются аналитические витрины и результаты обработки данных, используемые для проверки гипотез.

## 1.3. Архитектура обработки данных

В рамках проекта используется следующая архитектура:

`PostgreSQL / MongoDB → Apache Airflow → Apache Spark → Iceberg / MinIO → Trino → Superset`

Назначение компонентов:

| Компонент | Ответственность |
|---|---|
| PostgreSQL | Хранение структурированных игровых данных |
| MongoDB | Хранение событий и дополнительных игровых данных |
| Apache Airflow | Оркестрация и контроль выполнения процессов |
| Apache Spark | Очистка, преобразование и аналитическая обработка |
| Iceberg | Хранение аналитических таблиц |
| MinIO | Объектное хранение данных |
| Trino | Выполнение SQL-запросов |
| Superset | Визуализация результатов |
| Python / ML API | Обучение моделей и внешняя интеллектуальная обработка |

# 2. Общие требования SLA

## 2.1. Требования к входным данным

Все данные, используемые в аналитических кейсах, должны соответствовать следующим требованиям:

1. Источники данных должны быть доступны для чтения.
2. Структура таблиц должна соответствовать ожидаемой схеме.
3. Обязательные идентификаторы не должны содержать NULL.
4. Типы данных должны соответствовать требованиям обработки.
5. Дублирующиеся записи должны выявляться и обрабатываться.
6. Некорректные и неполные записи должны исключаться либо отдельно маркироваться.
7. Все преобразования должны сохранять логическую целостность данных.

Для каждой используемой таблицы необходимо определить:
- название источника;
- назначение;
- перечень обязательных полей;
- типы данных;
- первичные и логические ключи;
- правила очистки;
- допустимые значения.

## 2.2. Требования к Data Quality

Каждая аналитическая витрина должна проходить проверки качества данных.

| № | Проверка | Требование |
|---|---|---|
| 1 | Completeness | Обязательные поля заполнены |
| 2 | Uniqueness | Отсутствуют необработанные дубликаты ключевых записей |
| 3 | Validity | Значения соответствуют допустимым диапазонам |
| 4 | Consistency | Связанные показатели не противоречат друг другу |
| 5 | Referential Integrity | Связи между сущностями корректны |
| 6 | Accuracy | Расчёты соответствуют установленной бизнес-логике |
| 7 | Schema Validation | Структура таблиц соответствует ожидаемой схеме |

Каждая проверка должна иметь:
- название;
- описание;
- проверяемое поле или набор полей;
- условие успешного выполнения;
- результат проверки;
- действие при обнаружении ошибки.

## 2.3. Требования к ETL

ETL-процессы должны удовлетворять следующим требованиям:

- Реализация должна быть воспроизводимой.
- Повторный запуск не должен приводить к неконтролируемому размножению записей.
- Все ключевые преобразования должны быть документированы.
- Ошибки обработки должны фиксироваться.
- Должна быть предусмотрена проверка результата перед записью в целевую таблицу.
- Запись в Iceberg должна выполняться только после успешного прохождения обязательных проверок.
- Изменение схемы источника должно выявляться до формирования некорректной витрины.

## 2.4. Требования к воспроизводимости

Для каждого кейса необходимо сохранять:

1. Исходный код обработки данных.
2. SQL-запросы и параметры фильтрации.
3. Версии используемых библиотек.
4. Параметры ML-моделей.
5. Конфигурацию обработки.
6. Результаты проверок качества.
7. Версию аналитической витрины.

При использовании внешних API дополнительно фиксируются модель, версия API, параметры запроса и идентификатор обработки без сохранения секретных ключей.

## 2.5. Требования к Lineage

Для каждой итоговой витрины необходимо обеспечивать прослеживаемость данных:

`Источник → Преобразование → Аналитическая витрина → Trino → Superset`

Lineage должен позволять определить:
- из каких таблиц получены данные;
- какие фильтры применялись;
- какие преобразования выполнялись;
- какие бизнес-метрики рассчитывались;
- в какой итоговой витрине сохранён результат.

## 2.6. Требования к результатам

Итоговые витрины должны:
- иметь уникальную идентификацию;
- соответствовать согласованной схеме;
- содержать только данные, прошедшие обязательные проверки;
- быть доступны через Trino;
- иметь документированную бизнес-логику;
- обеспечивать возможность повторного получения аналитического результата.

| Показатель | Целевое значение |

## 3.5. Время реакции на инциденты

Время реакции — период от обнаружения проблемы до начала её обработки ответственным участником команды.

| Приоритет | Описание | Время реакции |
|---|---|---:|
| P1 — Критический | Полная недоступность хранилища или основных процессов | ≤ 30 минут |
| P2 — Высокий | Не формируется аналитическая витрина | ≤ 2 часов |
| P3 — Средний | Ошибка отдельной метрики или части данных | ≤ 8 рабочих часов |
| P4 — Низкий | Ошибки документации и незначительные проблемы | ≤ 2 рабочих дней |

## 3.6. Время восстановления

Время восстановления — период от обнаружения проблемы до восстановления работоспособности затронутого компонента или публикации корректного результата.

| Приоритет | Описание | Время восстановления |
|---|---|---:|
| P1 — Критический | Полная недоступность системы | ≤ 4 часов |
| P2 — Высокий | Ошибка формирования витрины | ≤ 8 часов |
| P3 — Средний | Ошибка отдельной метрики | ≤ 2 рабочих дней |
| P4 — Низкий | Некритичная ошибка документации | ≤ 5 рабочих дней |

Восстановление считается завершённым только после повторного прохождения необходимых проверок качества.

## 3.7. Требования к повторному запуску

| Параметр | Норматив |
|---|---|
| Количество автоматических повторных попыток | До 3 |
| Интервал между попытками | 5–15 минут |
| Повторный запуск после исправления ошибки | В течение 30 минут |
| Контрольная проверка после запуска | Обязательна |
| Публикация некорректной витрины | Запрещена |

Количество попыток и интервалы могут изменяться в зависимости от типа ошибки и ограничений источников данных.

# 4. Классификация инцидентов

Для всех аналитических кейсов применяется единая система приоритетов.

| Приоритет | Уровень | Описание | Пример |
|---|---|---|---|
| P1 | Критический | Результат полностью недоступен или существенно недостоверен | Повреждение витрины, массовая ошибка расчётов |
| P2 | Высокий | Нарушена основная функциональность кейса | ETL завершился ошибкой, модель не сформировала результат |
| P3 | Средний | Частичная ошибка, не препятствующая использованию всего результата | Некорректно рассчитана отдельная метрика |
| P4 | Низкий | Незначительная проблема документации или представления | Ошибка описания поля |

При возникновении инцидента необходимо:

1. Зафиксировать проблему.
2. Определить затронутые данные и витрины.
3. Установить приоритет.
4. Определить причину возникновения.
5. Устранить ошибку.
6. Повторно выполнить проверки качества.
7. Зафиксировать результат восстановления.

Сроки реакции и восстановления определяются в соответствии с разделом 3.

# 5. SLA кейса №3 — Корреляция между временем убийства Рошана и победой

## 5.1. Описание кейса

**Цель:** определить взаимосвязь между временем убийства Рошана, количеством убийств и вероятностью победы команды.

Кейс предназначен для проверки игровых гипотез, связанных с влиянием контроля Рошана на результат матча.

## 5.2. Источники данных

| Источник | Назначение | Используемые данные |
|---|---|---|
| `cs_events` | События убийства Рошана | `npcId = 133`, время события, идентификатор убийцы |
| `gold_events` | Командное золото за Рошана | `reason = 'ROSHAN'` |
| `matches` | Результаты матчей | `match_id`, `radiant_win`, `duration` |
| `match_players` | Информация об игроках | `match_id`, `account_id`, `player_slot` |

Основные источники:
- События Рошана определяются по `npcId = 133`.
- Командное золото определяется по `reason = 'ROSHAN'`.
- Победа определяется по полю `radiant_win`.

## 5.3. Проверка входных данных

| № | Проверка | Условие |
|---|---|---|
| 1 | Идентификатор матча | `match_id IS NOT NULL` |
| 2 | Идентификатор события | `id IS NOT NULL` |
| 3 | Тип события | `npcId = 133` |
| 4 | Исключение иллюзий | `isFromIllusion = false` или NULL согласно правилам источника |
| 5 | Длительность матча | `duration > 0` |
| 6 | Время события | `0 <= roshan_time <= duration` |
| 7 | Результат матча | `radiant_win` содержит допустимое булево значение |
| 8 | Уникальность события | Один актуальный экземпляр события по `match_id + id` |

При наличии нескольких версий события должна использоваться актуальная запись по `sys_insert_stamp`.

## 5.4. Требования к обработке

Обработка должна обеспечивать:

1. Очистку и дедупликацию матчей.
2. Очистку и дедупликацию игроков.
3. Выделение событий убийства Рошана.
4. Исключение событий иллюзий.
5. Определение стороны убийцы.
6. Исключение событий с некорректным временем.
7. Определение первого и последнего убийства Рошана.
8. Расчёт общего количества убийств.
9. Расчёт количества убийств по сторонам.
10. Расчёт итоговых бизнес-метрик.

Если убийцу невозможно сопоставить с игроком, событие должно сохраняться с признаком неизвестной стороны.

## 5.5. Бизнес-гипотезы

| № | Гипотеза | Проверяемый результат |
|---|---|---|
| 1 | Первый Рошан до 20-й минуты увеличивает вероятность победы более чем на 15% | Разница вероятностей победы между группами |
| 2 | Контроль Рошана увеличивает вероятность победы более чем на 25% | Сравнение результатов команд с контролем и без него |
| 3 | Убийство Рошана после 45-й минуты оказывает слабое влияние на исход матча | Сравнение вероятностей победы для поздних убийств |

Указанные проценты являются порогами проверяемых гипотез, а не гарантированными результатами.

## 5.6. Требования к аналитическим метрикам

| Метрика | Описание |
|---|---|
| `first_roshan_time` | Время первого убийства Рошана |
| `last_roshan_time` | Время последнего убийства Рошана |
| `total_roshan_kills` | Общее количество убийств |
| `roshan_killed_by_radiant` | Убийства командой Radiant |
| `roshan_killed_by_dire` | Убийства командой Dire |
| `roshan_killer_side_unknown` | Убийства с неизвестной стороной |
| `unknown_side_ratio` | Доля событий с неизвестной стороной |
| `first_roshan_time_bin` | Временной интервал первого убийства |
| `has_early_roshan` | Наличие раннего убийства |
| `roshan_control_status` | Статус контроля Рошана |

Временная сегментация:
- 0–15 минут;
- 15–25 минут;
- 25–35 минут;
- 35+ минут.

## 5.7. Требования к Data Quality

| № | Проверка | Условие приёмки |
|---|---|---|
| 1 | Уникальность матчей | Один `match_id` на запись |
| 2 | Уникальность событий | Нет повторного учёта одного события |
| 3 | Временные ограничения | Время убийства находится в пределах матча |
| 4 | Согласованность убийств | Сумма убийств по сторонам и неизвестным убийцам равна общему количеству |
| 5 | Доля неизвестной стороны | Рассчитывается и документируется |
| 6 | Первый Рошан | Выбирается минимальное время события |
| 7 | Последний Рошан | Выбирается максимальное время события |
| 8 | Статус контроля | Соответствует количеству убийств каждой команды |

Ключевая проверка:

`roshan_killed_by_radiant + roshan_killed_by_dire + roshan_killer_side_unknown = total_roshan_kills`

Для всех записей итоговой витрины должно выполняться условие `is_sum_valid = true`.

Если событий Рошана нет, счётчики должны быть равны нулю, а временные показатели — NULL.

## 5.8. Требования к статистической корректности

Для подтверждения гипотез необходимо:
- сравнивать сопоставимые группы матчей;
- учитывать длительность матча;
- учитывать сторону команды;
- учитывать размер выборки;
- фиксировать количество наблюдений;
- рассчитывать разницу вероятностей победы;
- при необходимости проверять статистическую значимость;
- учитывать возможные смешивающие факторы.

Нельзя трактовать обнаруженную корреляцию как доказательство причинно-следственной связи.

## 5.9. Время выполнения и критерии приёмки

Предполагаемые нормативы:

| Показатель | Значение |
|---|---:|
| Периодичность обновления | 1 раз в сутки |
| Максимальное время ETL | 2 часа |
| Проверка Data Quality | До 15 минут |
| Публикация результата | До 09:00 |
| Повторный запуск при ошибке | До 30 минут после обнаружения |

Кейс считается прошедшим приёмку, если:

1. Все обязательные источники доступны.
2. Выполнена очистка и дедупликация.
3. События Рошана корректно определяются.
4. Сторона убийцы определяется либо маркируется как неизвестная.
5. Все обязательные бизнес-метрики рассчитаны.
6. Проверка `is_sum_valid` проходит для всех записей.
7. Итоговая витрина успешно сохраняется в Iceberg.
8. Результаты доступны через Trino.
9. Гипотезы сопровождаются статистическим обоснованием.

# 6. SLA кейса №20 — Сегментация героев по пику и контр-пику (ALS)

## 6.1. Описание кейса

**Цель:** разработать рекомендательную модель, которая позволяет оценивать совместимость героев и выявлять потенциально эффективные пики и контр-пики.

В качестве основного алгоритма используется ALS (Alternating Least Squares) — метод факторизации матрицы взаимодействий.

В рамках данного кейса ALS используется вместо подхода с построением ручной матрицы, PCA и последующим расчётом cosine similarity.

## 6.2. Источники данных

Основной источник:

`lakehouse.raw.pg__match_players`

| Поле | Назначение |
|---|---|
| `match_id` | Идентификатор матча |
| `hero_id` | Идентификатор выбранного героя |
| `radiant_win` | Результат матча |
| `player_slot` | Определение стороны игрока |

Определение стороны:
- Radiant Pick: `player_slot < 128`.
- Dire Pick: `player_slot >= 128`.

Целевая переменная результата матча — `radiant_win`.

## 6.3. Проверка входных данных

| № | Проверка | Условие |
|---|---|---|
| 1 | Идентификатор матча | `match_id IS NOT NULL` |
| 2 | Идентификатор героя | `hero_id IS NOT NULL` |
| 3 | Слот игрока | Значение соответствует допустимому диапазону |
| 4 | Результат матча | `radiant_win` является корректным булевым значением |
| 5 | Уникальность выбора | Один игрок не должен иметь несколько конфликтующих записей выбора в одном матче |
| 6 | Состав команды | Не более пяти игроков на каждой стороне |
| 7 | Идентификаторы героев | Все `hero_id` присутствуют в справочнике героев |

Необходимо исключать некорректные матчи и записи с отсутствующими идентификаторами.

## 6.4. Требования к построению рекомендательной модели

Основной алгоритм — ALS.

Модель должна:

1. Формировать обучающую выборку из исторических матчей.
2. Строить взаимодействия между объектами рекомендательной системы и героями.
3. Обучать ALS с фиксированными параметрами.
4. Сохранять параметры и версию обученной модели.
5. Формировать оценки совместимости героев.
6. Выдавать рекомендации по пику и контр-пику.
7. Обеспечивать воспроизводимость результатов.

При проектировании необходимо отдельно определить, что является пользователем (`user`), а что объектом рекомендации (`item`).

Обычная ALS-факторизация по совместной встречаемости героев не доказывает, что один герой является контр-пиком другого. Для определения контр-пиков необходимо учитывать результат противостояния и использовать его при формировании обучающих взаимодействий, оценке пар героев или ранжировании рекомендаций.

## 6.5. Требования к обучению модели

| Параметр | Требование |
|---|---|
| Алгоритм | ALS |
| Количество факторов | Фиксируется в конфигурации |
| Регуляризация | Фиксируется в конфигурации |
| Число итераций | Фиксируется в конфигурации |
| Источник обучения | Исторические матчи |
| Обучающая выборка | Документированная и очищенная |
| Версия модели | Обязательно фиксируется |
| Результат | Сохранённая модель и рекомендации |

Запрещается использовать информацию о результате матча в признаках, доступных рекомендательной системе на момент принятия решения, если это создаёт утечку целевой переменной.

## 6.6. Требования к оценке модели

Оценка модели должна выполняться на данных, не участвовавших в обучении.

Рекомендуется использовать разделение по матчам, а не случайное разделение отдельных строк одного матча.

Основные показатели:

| Метрика | Назначение |
|---|---|
| Precision@K | Доля релевантных героев среди первых K рекомендаций |
| Recall@K | Полнота найденных релевантных рекомендаций |
| NDCG@K | Качество ранжирования рекомендаций |
| Coverage | Доля героев, для которых модель формирует рекомендации |
| Win Rate | Доля побед для анализируемых комбинаций героев |

Для оценки именно контр-пиков необходимо отдельно проверять эффективность рекомендаций против конкретного состава противника.

## 6.7. Требования к Data Quality

| № | Проверка | Условие приёмки |
|---|---|---|
| 1 | Корректность идентификаторов | Нет NULL в ключевых полях |
| 2 | Уникальность игроков | Нет конфликтующих записей выбора |
| 3 | Корректность состава | Не более пяти героев на сторону |
| 4 | Корректность сторон | Правильно определяются Radiant и Dire |
| 5 | Отсутствие утечки | Результат матча не попадает в недопустимые признаки |
| 6 | Разделение выборок | Тестовые матчи не участвуют в обучении |
| 7 | Воспроизводимость | Одинаковая конфигурация и данные позволяют повторить обучение |
| 8 | Корректность рекомендаций | Нет неизвестных или недопустимых `hero_id` |

## 6.8. Требования к результату

Результат должен содержать:
- идентификатор рассматриваемого состава;
- рекомендованных героев;
- оценки или ранги рекомендаций;
- тип рекомендации (пик / контр-пик);
- версию модели;
- параметры обучения;
- показатели качества модели.

Для каждого результата должна быть возможность установить, на основании какой версии модели он получен.

## 6.9. Время выполнения и критерии приёмки

Предполагаемые нормативы:

| Показатель | Значение |
|---|---:|
| Обновление обучающей выборки | 1 раз в сутки |
| Максимальное время подготовки данных | 30 минут |
| Максимальное время обучения модели | 2 часа |
| Максимальное время формирования рекомендаций | 15 минут |
| Проверка качества модели | До 30 минут |
| Публикация результата | До 09:00 |

Кейс считается прошедшим приёмку, если:

1. Входные данные прошли проверки качества.
2. Корректно определяются стороны команд.
3. Обучение выполняется с использованием ALS.
4. Параметры модели зафиксированы.

7. Сформированы рекомендации по героям.
8. Качество рекомендаций рассчитано и документировано.

10. Результаты доступны для дальнейшего анализа.

# 7. SLA кейса №21 — Классификация ников игроков (LLM via API)

## 7.1. Описание кейса

**Цель:** использовать языковую модель через внешний API для автоматической классификации игровых никнеймов.

LLM должна анализировать текст никнейма и определять его принадлежность к заранее установленным тематическим категориям.

Классификация должна выполняться с учётом контекста и установленных правил разметки.

## 7.2. Источники данных

| Источник | Назначение | Используемые данные |
|---|---|---|
| `raw_players` | Данные игроков | `account_id`, `persona` и другие доступные поля |
| `match_players` | Игровая статистика | Статистика участия игрока в матчах |
| Дополнительный справочник | История никнеймов | Связь никнейма с `account_id` |

Схема источников и точные названия дополнительных полей должны быть подтверждены по фактической структуре таблиц.

## 7.3. Проверка входных данных

| № | Проверка | Условие |
|---|---|---|
| 1 | Идентификатор игрока | `account_id IS NOT NULL` |
| 2 | Никнейм | Поле `persona` доступно для обработки |
| 3 | Текст никнейма | Отсутствуют пустые и некорректные значения |
| 4 | Уникальность | Исключены необработанные дубликаты |
| 5 | История никнеймов | Сохраняется связь с соответствующим игроком |
| 6 | Контекст | Дополнительная статистика связана с правильным `account_id` |

Никнеймы должны обрабатываться как текстовые данные. Их содержимое не должно интерпретироваться как исполняемый код или инструкции для системы.

## 7.4. Требования к классификации

LLM должна:

1. Получать никнейм в установленном формате.
2. Анализировать его содержание.
3. Определять соответствующую тематическую категорию.
4. Возвращать структурированный результат.
5. Не добавлять произвольные категории.
6. Возвращать статус неопределённости, если классификация невозможна.
7. Сохранять результат обработки для дальнейшего анализа.

Набор категорий должен быть заранее утверждён и описан в справочнике классификации.

Если никнейм подходит сразу под несколько категорий, правила обработки должны определять возможность множественной классификации либо выбор основной категории.

## 7.5. Требования к API

| № | Требование | Описание |
|---|---|---|
| 1 | Доступность API | Обработка ошибок подключения |
| 2 | Валидация запроса | Передача корректного формата данных |
| 3 | Валидация ответа | Проверка структуры ответа модели |
| 4 | Таймауты | Ограничение времени ожидания |
| 5 | Повторные запросы | Retry при временных ошибках |
| 6 | Ограничение запросов | Соблюдение лимитов API |
| 7 | Обработка ошибок | Отдельная фиксация неуспешных запросов |
| 8 | Безопасность | Защита API-ключей и конфиденциальных данных |

Повторный запрос не должен приводить к неконтролируемому дублированию результатов классификации.

При временной недоступности API задача должна завершаться контролируемой ошибкой либо сохранять записи в очередь повторной обработки.

## 7.6. Требования к результатам классификации

| Поле | Назначение |
|---|---|
| `account_id` | Идентификатор игрока |
| `nickname` | Исходный никнейм |
| `predicted_category` | Предсказанная категория |
| `confidence` | Оценка уверенности, если поддерживается моделью |
| `model_name` | Название модели |
| `model_version` | Версия модели |
| `processing_status` | Статус обработки |
| `error_message` | Описание ошибки при наличии |

Если используемая модель не предоставляет достоверную калиброванную вероятность, значение `confidence` не должно трактоваться как вероятность правильной классификации.

## 7.7. Требования к Data Quality

| № | Проверка | Условие приёмки |
|---|---|---|
| 1 | Полнота входных данных | Все записи имеют идентификатор игрока |
| 2 | Корректность никнейма | Нет пустых значений в обрабатываемой выборке |
| 3 | Связь с игроком | Никнейм связан с корректным `account_id` |
| 4 | Валидность категории | Категория присутствует в утверждённом справочнике |
| 5 | Формат ответа | API возвращает допустимую структуру |
| 6 | Обработка ошибок | Ошибки API фиксируются |
| 7 | Повторная обработка | Нет неконтролируемых дубликатов |
| 8 | Воспроизводимость | Сохраняется информация о версии модели |

## 7.8. Требования к оценке качества LLM

Качество классификации должно проверяться на контрольной выборке с заранее подготовленной ручной разметкой.

Основные метрики:

| Метрика | Назначение |
|---|---|
| Accuracy | Общая доля правильных классификаций |
| Precision | Точность определения конкретной категории |
| Recall | Полнота определения конкретной категории |
| F1-score | Баланс Precision и Recall |
| Confusion Matrix | Анализ ошибок между категориями |

Для многоклассовой классификации необходимо дополнительно оценивать качество по каждой категории, а не только общую Accuracy.

Результаты автоматической классификации должны сохраняться отдельно от эталонной разметки.

## 7.9. Время выполнения и критерии приёмки

Предполагаемые нормативы:

| Показатель | Значение |
|---|---:|
| Подготовка данных | До 15 минут |
| Максимальное время обработки одной партии API-запросов | 2 часа |
| Таймаут одного API-запроса | 60 секунд |
| Количество повторных попыток | До 3 |
| Проверка результатов классификации | До 30 минут |
| Публикация итоговой витрины | До 09:00 |

Время обработки одной партии зависит от размера выборки, лимитов API и используемой модели.

Кейс считается прошедшим приёмку, если:

1. Источники данных доступны.
2. Никнеймы корректно связаны с игроками.
3. Выполнена очистка текстовых данных.
4. API принимает запросы в установленном формате.
5. Ответы модели проходят структурную валидацию.
6. Используются только утверждённые категории.
7. Ошибки API корректно обрабатываются.
8. Результаты сохраняются в аналитическом хранилище.
9. Качество классификации проверено на размеченной выборке.
10. Версия модели и результаты обработки документированы.

- количество обработанных записей;

При обнаружении ошибки:

1. Определить этап обработки, на котором она возникла.
2. Проверить исходные данные.
3. Проверить логи соответствующего процесса.
4. Установить причину ошибки.
5. Исправить проблему.
6. Повторно запустить обработку при необходимости.
7. Проверить корректность результата.
8. Зафиксировать устранение проблемы.

Результат не должен считаться успешным только на основании статуса `Success` в Airflow. Обязательным условием является прохождение проверок качества итоговой витрины.
