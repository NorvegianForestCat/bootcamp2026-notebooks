# Model Risk Management (MRM) Policy

**Версия:** 1.0 (Draft)  
**Область:** ML-модели кейсов №20 (ALS), №22 (supervised classification), №21 (LLM classification)  
**Регуляторный драйвер:** CBR 657-P, SR 11-7, Basel Committee  
**Статус:** Проект документа

---

## 1. Цель и область применения

Настоящая политика устанавливает требования к разработке, валидации, внедрению, мониторингу и выводу из эксплуатации ML-моделей, используемых в аналитических кейсах буткемпа 2026.

Кейсы, подлежащие MRM:
| № | Название | Тип модели | Назначение |
|---|----------|------------|------------|
| №20 | Сегментация героев по пику и контр-пику | ALS (Alternating Least Squares) | Collaborative filtering, рекомендация героев |
| №22 | Пики и контр-пики (ML) | Supervised classification (LogReg / CatBoost) | Предсказание победы Radiant по драфту |
| №21 | Классификация ников (LLM) | LLM API (classification) | Классификация никнеймов по типам |

---

## 2. Жизненный цикл модели

### 2.1 Разработка (Development)

Требования:
- Обучающая выборка документирована и очищена (DQ проверки пройдены).
- Версия обучающих данных зафиксирована (Iceberg snapshot или watermark).
- Гиперпараметры зафиксированы в конфигурации.
- Отсутствует утечка целевой переменной (leakage protection).

**Конкретные требования по кейсам:**
- **№20 (ALS):** разделение пользователей/героев, фиксированные rank, maxIter, regParam; исключение утечки через целевую переменную в признаках.
- **№22 (Supervised):** временное разбиение train/test по `start_time` (не случайное по строкам); target encoding только внутри train (out-of-fold); geen post-match признаков (KDA, GPM, финальный rank) в признаках для предсказания до драфта.
- **№21 (LLM):** фиксация модели API, версии, температуры, промпта; валидация JSON-схемы ответа; доля ошибок API не более 5% (DQ-CASE21-04).

### 2.2 Валидация (Validation)

Обязательные проверки перед внедрением:

| Проверка | Описание | Критерий прохождения |
|----------|----------|---------------------|
| **Стабильность** | Результаты воспроизводятся при повторном запуске на тех же данных | 100% контрольных запусков |
| **Качество** | Метрики на тестовой выборке соответствуют порогам | Precision@K, Recall@K, NDCG, ROC-AUC ≥ заданного порога |
| **Отсутствие утечки** | Целевая переменная не попадает в признаки | Проверка кода и признаков |
| **Дрифт** | Распределение признаков на inference близко к обучении | Статистически значимых отличий нет |
| **Покрытие** | Все ключевые сегменты покрыты выборкой | Нет «холодных» объектов с 0 наблюдений (DQ-CASE20-02) |

### 2.3 Внедрение (Deployment)

- Модель сохраняется с версией и параметрами обучения.
- Результат содержит идентификатор версии модели.
- Возможен откат на предыдущую версию.
- Доступ к модели ограничен (RBAC).

### 2.4 Мониторинг (Monitoring)

Ежедневный мониторинг:
- Качество предсказаний на новых данных.
- Доля ошибок API (для LLM).
- Дрифт признаков и целевой переменной.
- Время выполнения (SLA: обучение модели ≤ 2 часа, формирование рекомендаций ≤ 15 минут).

### 2.5 Вывод из эксплуатации (Decommissioning)

Модель выводится из эксплуатации если:
- Качество снижается ниже порога на 3 последовательных запуска.
- Источник данных изменён и несовместим с моделью.
- Выявлена критическая утечка или ошибка в логике.

## 3. Модельные карты (Model Cards)

Каждая модель должна иметь Model Card со следующими полями:

| Поле | Описание |
|------|----------|
| `model_id` | Уникальный идентификатор модели |
| `version` | Версия (например `v1.0`) |
| `case` | Номер кейса (№20, №22, №21) |
| `algorithm` | Алгоритм (ALS, Logistic Regression, CatBoost, LLM API) |
| `training_data` | Источник, период, количество записей |
| `hyperparameters` | Фиксированные гиперпараметры |
| `metrics` | Метрики качества на тестовой выборке |
| `limitations` | Ограничения и известные проблемы |
| `owner` | Ответственный разработчик |
| `created_at` | Дата обучения |
| `retired_at` | Дата вывода из эксплуатации (если применимо) |

---

## 4. Роли и ответственность

| Роль | Ответственность |
|------|-----------------|
| **Data Scientist** | Разработка модели, подбор гиперпараметров, обучение |
| **ML Engineer** | Внедрение, мониторинг, инфраструктура |
| **Data Engineer** | Подготовка данных, DQ проверки, pipeline |
| **Model Owner** | Ответственность за модель на всём жизненном цикле |
| **Risk Reviewer** | Независимая проверка перед внедрением |

---

## 5. Связь со SLA

MRM политика дополняет SLA (разделы 6–7):
- Успешность запусков ETL ≥ 95%.
- Обязательные DQ-проверки проходят для 100% витрин.
- Воспроизводимость обработки 100% контрольных повторных запусков.
- Наличие lineage 100% описанных витрин.

---

## 6. Исключения и апелляции

Любое отклонение от политики требует:
- Документированного обоснования.
- Одобрения Model Owner и Risk Reviewer.
- Фиксации в журнале исключений с датой и сроком действия.
