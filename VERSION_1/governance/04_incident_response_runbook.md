# Incident Response Runbook — Аналитические кейсы Dota 2

**Версия:** 1.0 (Draft)  
**Область:** Lakehouse, Airflow, Spark, Trino, Superset, ML-пайплайны  
**База:** `sla.md` (раздел 4 — классификация инцидентов P1–P4)  
**Статус:** Проект документа

---

## 1. Цель

Единая процедура реагирования на инциденты: фиксация, классификация, эскалация, устранение, восстановление, документирование.

---

## 2. Классификация инцидентов (из SLA)

| Приоритет | Уровень | Описание | Пример | Время реакции | Время восстановления |
|-----------|---------|----------|--------|---------------|----------------------|
| **P1** | Критический | Полная недоступность или существенная недостоверность результата | Повреждение витрины, массовая ошибка расчётов | ≤ 30 мин | ≤ 4 ч |
| **P2** | Высокий | Нарушена основная функциональность кейса | ETL завершился ошибкой, модель не дала результат | ≤ 2 ч | ≤ 8 ч |
| **P3** | Средний | Частичная ошибка, не препятствующая использованию результата | Некорректно рассчитана отдельная метрика | ≤ 8 раб. ч | ≤ 2 раб. дня |
| **P4** | Низкий | Незначительная проблема документации или представления | Ошибка описания поля в Data Dictionary | ≤ 2 раб. дня | ≤ 5 раб. дней |

## 3. Процедура реагирования

### Шаг 1 — Фиксация проблемы

Создать запись в инцидентном журнале (Jira/GitHub Issues/другой инструмент):

| Поле | Описание |
|------|----------|
| `incident_id` | Уникальный ID |
| `title` | Краткое название |
| `priority` | P1–P4 |
| `detected_at` | Время обнаружения |
| `detected_by` | Кто обнаружил |
| `affected_datasets` | Затронутые таблицы/витрины |
| `affected_cases` | Затронутые кейсы (№3, №20, №21, №22) |
| `description` | Описание проблемы |
| `initial_impact` | Первичная оценка влияния |

### Шаг 2 — Классификация приоритета

Использовать таблицу из раздела 2. Если неясно — присвоить более высокий приоритет.

### Шаг 3 — Эскалация

| Приоритет | Эскалация | Канал уведомления |
|-----------|-----------|-------------------|
| P1 | Team Lead + Data Engineering Lead + Product Owner | Телефон/мессенджер (срочно) |
| P2 | Team Lead + Data Engineering Lead | Мессенджер + email |
| P3 | Team Lead | Мессенджер |
| P4 | Ответственный разработчик | Email / задача в трекере |

### Шаг 4 — Диагностика

Определить причину:
1. Проверить логи Airflow (DAG runs, task logs).
2. Проверить логи Spark (executor, driver).
3. Проверить DQ-проверки (какие правила упали: HARD или QUARANTINE).
4. Проверить lineage в Marquez (откуда пришли «плохие» данные).
5. Проверить Iceberg snapshots (какая версия витрины повреждена).

### Шаг 5 — Локализация (containment)

- Приостановить зависимые пайплайны (если есть риск распространения ошибки).
- Не удалять damaged витрину — оставить для форензики.
- Если необходимо — откатить на предыдущий Iceberg snapshot.

### Шаг 6 — Устранение

- Исправить код/данные/конфигурацию.
- Проверить, что исправление не вызывает регрессий.
- Получить одобрение Model Owner (для ML) или Data Engineering Lead (для ETL).

### Шаг 7 — Проверка качества

После устранения:
1. Запустить все обязательные DQ-проверки для затронутых витрин.
2. Убедиться, что `is_sum_valid = true` (для кейса №3).
3. Убедиться, что ML-метрики в порогах (для кейсов №20, №22).
4. Убедиться, что доля ошибок API ≤ 5% (для кейса №21).

### Шаг 8 — Восстановление

- Повторно запустить пайплайн.
- Убедиться, что витрина доступна через Trino.
- Убедиться, что Superset дашборд отображает корректные данные.
- Зафиксировать время восстановления.

### Шаг 9 — Документирование

Заполнить инцидентный отчёт:

| Поле | Описание |
|------|----------|
| `root_cause` | Корневая причина |
| `fix_description` | Описание исправления |
| `detection_time` | Время от обнаружения до начала обработки |
| `resolution_time` | Время от обнаружения до восстановления |
| `lessons_learned` | Уроки и профилактика |
| `follow_up_actions` | Действия для предотвращения повторения |

## 4. Специфичные сценарии

### Сценарий A: DQ HARD FAIL в ETL

**Признаки:** Airflow задача упала с `[DQ HARD FAIL]`.

**Действия:**
1. Показать, какое правило упало (rule_id, description).
2. Количество нарушённых строк (bad_cnt/total_rows).
3. Исправить источник или правило очистки.
4. Повторно запустить с того же этапа (идемпотентно через MERGE INTO).

### Сценарий B: DQ QUARANTINE

**Признаки:** Строки изолированы в `stage.quarantine_*`.

**Действия:**
1. Проверить, почему строки попали в карантин.
2. Если данные можно восстановить — исправить и перезагрузить.
3. Если данные потеряны — задокументировать как потерю, уведомить заказчика.

### Сценарий C: Ошибка LLM API (кейс №21)

**Признаки:** Доля нераспарсенных ответов > 5% (DQ-CASE21-04).

**Действия:**
1. Проверить доступность API, ключи, лимиты.
2. Проверить формат запроса и ответа.
3. При временной недоступности — сохранить записи в очередь повторной обработки.
4. Не допускать неконтролируемого дублирования результатов.

### Сценарий D: Утечка целевой переменной в ML

**Признаки:** Метрики качества аномально высокие (ROC-AUC ≈ 1.0).

**Действия:**
1. Проверить признаки на наличие post-match данных (KDA, GPM, финальный rank).
2. Проверить разбиение train/test (тemporальное, не случайное).
3. Переобучить модель без утечки.
4. Задокументировать инцидент как P2/P1.

### Сценарий E: Повреждение Iceberg таблицы

**Признаки:** Ошибка чтения, некорректные данные в витрине.

**Действия:**
1. Проверить Iceberg snapshots.
2. Откатить на предыдущий корректный snapshot.
3. Проверить lineage (какое преобразование вызвало повреждение).
4. Повторно запустить преобразование.

## 5. Связь со SLA

- Время реакции и восстановления соответствуют SLA раздел 3.5–3.6.
- Количество автоматических повторных попыток: до 3.
- Интервал между попытками: 5–15 мин.
- Публикация некорректной витрины запрещена.
- Контрольная проверка после запуска обязательна.

## 8. Профилактика

- Ежедневный мониторинг DQ-проверок.
- Еженедельный обзор проваленных джоб Airflow.
- Ежемесячный обзор инцидентов и извлечение уроков.
- Регулярное тестирование отката (rollback) на staging.
